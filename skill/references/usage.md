# zcode-mcp 使用模式与委派最佳实践

## 核心理念:调用方思考,zcode 执行

外部 agent(GPT 等)负责:理解需求 → 拆解任务 → 逐个委派 → 审查结果 → 集成。
zcode 负责:在指定目录里读代码、改代码、跑命令、跑 git、自验证。

## zcode_run 调用要点

1. **永远传 `cwd`**(目标项目的绝对路径)。没有 cwd,zcode 无法做任何文件操作。
2. **prompt 要具体、自包含**:改什么文件/函数、遵循什么约定、如何验证(跑测试/编译)。外部 agent 不应假设 zcode 看得到自己这边的上下文。
3. **一个大任务拆成多次 zcode_run**,每次一个可验证的闭环;把上一次返回的 `session_id` 传回来继续,避免重复铺上下文。
4. **超时预算**:真实编码任务 2–10 分钟常见;按任务规模给 `timeout_ms`(默认 600000,上限 3600000)。注意 MCP 客户端自身也有工具超时,两边都要留够。
5. **mode 选择**:
   - `yolo`(默认):全自动,无确认,适合无头委派;信任调用方时用。
   - `guarded`:0.17+ 的策略门控模式,权限请求仍会被 server 自动拒绝(无头无法应答),失败即返回。
   - `plan`:只读分析——让外部模型先"问 zcode 这个代码库怎么回事"非常好用。
6. **model/reasoning**:`GLM-5.3` + `max` 是默认;简单机械改动可 `GLM-5.3-Flash` + `high` 省额度。

## 典型工作流(外部 agent 视角)

```
1. zcode_run(mode=plan): "分析 <cwd> 的模块结构,给出实现 X 的改造点清单"
2. (调用方基于清单规划)
3. zcode_run: "在 <cwd> 实现 <具体改动>,完成后跑 <验证命令> 并贴结果"
4. 失败/需补充 → zcode_run(session_id=上次的, "修正:...")
5. 审查 diff,继续下一个子任务
```

## 返回值解读

- 正文 = zcode 的最终答复;
- 尾部元数据:`session_id`(续接用)、`model`、`tools_used`、`tokens`、`duration`、`cwd`;
- `isError: true` 时正文含错误码与已产出的部分文本,参考 troubleshooting.md。
